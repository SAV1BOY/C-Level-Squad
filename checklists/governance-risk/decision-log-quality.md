# Checklist de Qualidade do Decision Log (Decision Log Quality)

## Propósito
Assegurar que toda decisão relevante tomada pelo C-Level Squad seja registrada com
rationale documentado, dissent capturado e rastreabilidade completa. Este checklist
garante memória organizacional, accountability e capacidade de aprender com decisões
passadas — boas ou ruins.

## Quando Aplicar
- Após toda decisão estratégica tomada em reuniões do C-Level Squad
- Após decisões de investimento, contratação sênior ou mudança de prioridade
- Quando uma decisão anterior precisa ser revisada ou revertida
- Na auditoria trimestral de qualidade do decision log
- Quando novos líderes precisam entender o histórico de decisões

## Agente Responsável
- **Primário:** Chief of Staff como guardião do decision log
- **Secundário:** O decision-maker principal de cada decisão registrada
- **Revisor:** CEO para validação de decisões estratégicas de alto impacto

## Checklist

### Seção 1 — Registro da Decisão (Decision Registration)
- [ ] Item 1: A decisão está registrada em até 24 horas após ser tomada
- [ ] Item 2: O título da decisão é descritivo e searchable (facilita busca futura)
- [ ] Item 3: A data exata da decisão está registrada
- [ ] Item 4: O contexto que levou à decisão está resumido (2-3 parágrafos)
- [ ] Item 5: O fórum onde a decisão foi tomada está identificado (reunião, async, 1:1)
- [ ] Item 6: A classificação da decisão está atribuída (estratégica, tática, operacional)
- [ ] Item 7: O nível de reversibilidade está indicado (Type 1: irreversível, Type 2: reversível)
- [ ] Item 8: Tags ou categorias foram atribuídas para facilitar busca e análise

### Seção 2 — Rationale e Evidências (Rationale Documentation)
- [ ] Item 9: O rationale principal está documentado em linguagem clara e objetiva
- [ ] Item 10: As opções consideradas estão listadas (não apenas a opção escolhida)
- [ ] Item 11: Prós e contras de cada opção estão documentados
- [ ] Item 12: Dados e evidências que suportaram a decisão estão referenciados
- [ ] Item 13: Premissas subjacentes (assumptions) estão explicitadas
- [ ] Item 14: O framework de decisão utilizado está indicado (se aplicável)
- [ ] Item 15: O trade-off principal está articulado (o que foi sacrificado pela escolha)
- [ ] Item 16: O nível de confiança na decisão está registrado (alto, médio, baixo)

### Seção 3 — Participantes e Dissent (Participants & Dissent)
- [ ] Item 17: Todos os participantes da decisão estão listados com seus papéis
- [ ] Item 18: O decision-maker final está identificado (quem teve a palavra final)
- [ ] Item 19: Vozes dissidentes foram registradas com seus argumentos
- [ ] Item 20: O método de resolução de dissent está documentado (votação, owner decides, consenso)
- [ ] Item 21: Participantes que se abstiveram têm o motivo registrado
- [ ] Item 22: Se a decisão foi unânime, isso está explicitamente registrado
- [ ] Item 23: Feedback pós-decisão de stakeholders afetados foi coletado

### Seção 4 — Impacto e Execução (Impact & Execution)
- [ ] Item 24: As ações resultantes da decisão estão listadas com owners e deadlines
- [ ] Item 25: O impacto esperado está quantificado (financeiro, operacional, estratégico)
- [ ] Item 26: Stakeholders que precisam ser notificados estão identificados
- [ ] Item 27: A comunicação da decisão foi planejada e executada
- [ ] Item 28: O impacto em OKRs e iniciativas em andamento está mapeado
- [ ] Item 29: Recursos necessários para executar a decisão estão alocados
- [ ] Item 30: Métricas de sucesso da decisão estão definidas para tracking futuro

### Seção 5 — Revisão e Aprendizado (Review & Learning)
- [ ] Item 31: Uma data de revisão da decisão está agendada (decision review date)
- [ ] Item 32: Critérios para considerar a decisão bem-sucedida ou mal-sucedida estão definidos
- [ ] Item 33: Se a decisão foi revertida, o motivo está documentado
- [ ] Item 34: Learnings de decisões passadas similares foram consultados antes de decidir
- [ ] Item 35: A decisão contribui para o corpus de aprendizado organizacional
- [ ] Item 36: Padrões de decisão recorrentes estão sendo identificados para criar playbooks

### Seção 6 — Qualidade do Log como Sistema (Log System Quality)
- [ ] Item 37: O decision log está acessível a todos os membros do C-Level Squad
- [ ] Item 38: O formato é padronizado e consistente entre todas as entradas
- [ ] Item 39: A busca por decisões passadas é eficiente (indexação adequada)
- [ ] Item 40: O decision log é revisado trimestralmente para qualidade e completude
- [ ] Item 41: Decisões antigas são arquivadas mas permanecem acessíveis
- [ ] Item 42: O log está integrado com outros sistemas (OKRs, project management)
- [ ] Item 43: Backup e versionamento do decision log estão garantidos

## Critérios de Aprovação
O decision log é considerado saudável quando:

1. **100% das decisões estratégicas estão registradas em até 24 horas**
2. **Mínimo de 90% dos itens das Seções 1 e 2 estão completos para cada entrada**
3. **Dissent é capturado em pelo menos 80% das decisões não-unânimes (Seção 3)**
4. **Todas as decisões têm actions com owners e deadlines (Seção 4)**
5. **Pelo menos 70% das decisões têm review date agendada (Seção 5)**
6. **O sistema de log está funcional e acessível (Seção 6)**
7. **Auditoria trimestral de qualidade foi realizada**

## O que Fazer se Falhar
Se a qualidade do decision log não atinge os critérios:

1. **Auditoria de completude:** Identificar quais decisões recentes não foram registradas
2. **Backfill:** Alocar tempo para registrar decisões que ficaram fora do log
3. **Simplificar template:** Se o template é muito longo, as pessoas evitam preencher — simplificar
4. **Automatizar:** Integrar captura de decisões com ferramentas de reunião (auto-extract)
5. **Accountability:** O Chief of Staff deve cobrar registro de cada decisão em cada reunião
6. **Role model:** CEO deve registrar suas decisões exemplarmente para criar cultura
7. **Training:** Oferecer sessão de 30 minutos sobre como registrar decisões efetivamente
8. **Incentivo:** Reconhecer publicamente boas práticas de documentação de decisões
