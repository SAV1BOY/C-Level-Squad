# Checklist de Qualidade de Execução de Projetos (Project Execution Quality)

## Propósito
Garantir que todo projeto estratégico gerenciado pelo C-Level Squad tenha milestones
definidos, owners claros, riscos gerenciados e caminhos de escalação estabelecidos.
Este checklist evita que projetos derrapem silenciosamente sem visibilidade adequada
da liderança executiva.

## Quando Aplicar
- No kick-off de qualquer projeto estratégico (classificado como Tier 1 ou Tier 2)
- Em cada milestone review durante a execução do projeto
- Quando um projeto muda de status para at-risk ou off-track
- Na revisão mensal de portfólio de projetos do C-Level
- No encerramento do projeto (project closure review)

## Agente Responsável
- **Primário:** Project Owner designado (geralmente um C-Level ou diretor)
- **Secundário:** Chief of Staff para monitoramento de portfólio
- **Revisor:** Sponsor executivo do projeto

## Checklist

### Seção 1 — Definição do Projeto (Project Definition)
- [ ] Item 1: O escopo do projeto está documentado com boundaries claros (in-scope vs. out-of-scope)
- [ ] Item 2: O business case está aprovado com ROI ou impacto estratégico quantificado
- [ ] Item 3: O sponsor executivo está designado e engajado
- [ ] Item 4: O project owner tem autoridade suficiente para tomar decisões operacionais
- [ ] Item 5: Success criteria estão definidos com métricas objetivas (não subjetivas)
- [ ] Item 6: O projeto está classificado por tier (Tier 1: estratégico, Tier 2: tático, Tier 3: operacional)
- [ ] Item 7: Stakeholders-chave estão identificados e mapeados (RACI matrix)
- [ ] Item 8: O charter do projeto está assinado pelos stakeholders principais

### Seção 2 — Milestones e Timeline
- [ ] Item 9: Milestones intermediários estão definidos (não apenas início e fim)
- [ ] Item 10: Cada milestone tem critérios de conclusão (definition of done) claros
- [ ] Item 11: O caminho crítico (critical path) está identificado e monitorado
- [ ] Item 12: Datas são realistas e baseadas em estimativas fundamentadas (não wishful thinking)
- [ ] Item 13: Buffer de contingência está incluído para milestones de alto risco
- [ ] Item 14: Dependências entre milestones estão mapeadas e gerenciadas
- [ ] Item 15: O timeline está visível e acessível para todos os envolvidos
- [ ] Item 16: Mudanças no timeline são documentadas com razão e aprovadas pelo sponsor

### Seção 3 — Ownership e Accountability
- [ ] Item 17: Cada workstream tem um owner claro e único (single-threaded ownership)
- [ ] Item 18: Cada deliverable tem um responsável direto com deadline associado
- [ ] Item 19: A matriz RACI está documentada e comunicada a todos os envolvidos
- [ ] Item 20: Substitutos estão designados para owners críticos (bus factor > 1)
- [ ] Item 21: Decisão sobre quem tem authority final em disputas está clara
- [ ] Item 22: Accountability é verificada semanalmente nos check-ins de projeto

### Seção 4 — Gestão de Riscos (Risk Management)
- [ ] Item 23: Risk register está criado e atualizado com frequência mínima semanal
- [ ] Item 24: Cada risco tem probabilidade, impacto e owner designado
- [ ] Item 25: Os top 5 riscos possuem plano de mitigação documentado
- [ ] Item 26: Trigger points para ativação de planos de contingência estão definidos
- [ ] Item 27: Riscos de dependência externa (vendors, partners, regulação) estão mapeados
- [ ] Item 28: O impacto financeiro dos riscos principais está quantificado
- [ ] Item 29: Novos riscos são adicionados ao register conforme surgem (processo vivo)
- [ ] Item 30: Riscos mitigados ou expirados são movidos para arquivo com aprendizados

### Seção 5 — Escalação e Comunicação (Escalation & Communication)
- [ ] Item 31: O caminho de escalação está definido (quem escala, para quem, quando)
- [ ] Item 32: Critérios de escalação estão claros (não depende de julgamento subjetivo)
- [ ] Item 33: Tempo máximo de resposta para escalações está definido (SLA de escalação)
- [ ] Item 34: Status report semanal é enviado ao sponsor e stakeholders-chave
- [ ] Item 35: O formato de status report é padronizado (traffic light + blockers + decisions needed)
- [ ] Item 36: Comunicação para stakeholders mais amplos acontece em cadência definida
- [ ] Item 37: Bad news é comunicada mais rápido que good news (no surprises policy)
- [ ] Item 38: Mudanças de escopo são comunicadas imediatamente ao sponsor

### Seção 6 — Recursos e Capacidade (Resources & Capacity)
- [ ] Item 39: Budget do projeto está aprovado e alocado
- [ ] Item 40: Headcount necessário está disponível e committed
- [ ] Item 41: Ferramentas e infraestrutura necessárias estão provisionadas
- [ ] Item 42: Capacidade do time não está sobrecarregada (utilization abaixo de 85%)
- [ ] Item 43: Treinamentos necessários para o time foram realizados antes do kick-off
- [ ] Item 44: Custos estão sendo trackeados contra o budget aprovado

### Seção 7 — Encerramento (Project Closure)
- [ ] Item 45: Todos os deliverables foram entregues e aceitos pelo sponsor
- [ ] Item 46: Postmortem ou retrospectiva foi realizada com o time completo
- [ ] Item 47: Learnings foram documentados e compartilhados com a organização
- [ ] Item 48: Handoff para operação (se aplicável) foi realizado com documentação
- [ ] Item 49: Métricas de sucesso são monitoradas por pelo menos 90 dias após encerramento

## Critérios de Aprovação
A execução do projeto é considerada saudável quando:

1. **Mínimo de 85% dos itens aplicáveis ao estágio atual do projeto estão completos**
2. **100% dos itens das Seções 1 e 3 estão completos** (definição e ownership são obrigatórios)
3. **Risk register (Seção 4) está atualizado e revisado na última semana**
4. **Status reports (Seção 5) estão sendo enviados no prazo**
5. **Nenhum milestone crítico está atrasado sem plano de recuperação documentado**
6. **O sponsor confirma estar informado e alinhado com o estado do projeto**
7. **Escalações pendentes foram resolvidas dentro do SLA definido**

## O que Fazer se Falhar
Se o projeto não atinge os critérios de qualidade:

1. **Triage imediato:** Classificar a severidade do gap (yellow warning ou red alert)
2. **Sponsor meeting:** Convocar reunião urgente com sponsor para apresentar situação
3. **Recovery plan:** Criar plano de recuperação com ações específicas e deadlines
4. **Resource reallocation:** Se o problema é de capacidade, realocar recursos temporariamente
5. **Scope negotiation:** Considerar redução de escopo para proteger timeline e qualidade
6. **External help:** Se o gap é de capability, considerar consultoria ou contratação temporária
7. **Kill decision:** Se o projeto é irrecuperável, apresentar ao sponsor com recomendação de cancelar
8. **Documentar:** Registrar a falha, causas e ações no project log e decision log
