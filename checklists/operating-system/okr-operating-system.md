# Checklist do Sistema Operacional de OKRs (OKR Operating System)

## Propósito
Garantir que o sistema operacional de OKRs — desde a definição até a revisão —
esteja funcionando corretamente, com cadência estabelecida, responsabilidades claras
e ciclos de review produtivos. Este checklist verifica a saúde do processo, não
apenas o conteúdo dos OKRs individuais.

## Quando Aplicar
- No início de cada ciclo de OKRs (trimestral)
- Na metade do ciclo (mid-quarter health check)
- No fechamento do ciclo (retrospectiva antes do próximo)
- Quando há sinais de que o sistema de OKRs está perdendo tração
- Após mudanças organizacionais significativas (reorgs, novas lideranças)

## Agente Responsável
- **Primário:** Chief of Staff ou OKR Champion designado
- **Secundário:** Cada Squad Lead como responsável pelo OKR do seu squad
- **Revisor:** CEO para validação do sistema no nível empresa

## Checklist

### Seção 1 — Definição de OKRs (OKR Setting)
- [ ] Item 1: OKRs do nível empresa foram definidos antes dos OKRs de squad
- [ ] Item 2: Cada squad definiu seus OKRs dentro do prazo estabelecido (max 2 semanas após empresa)
- [ ] Item 3: O número de Objectives por squad está entre 2 e 4
- [ ] Item 4: Cada Objective tem entre 2 e 5 Key Results mensuráveis
- [ ] Item 5: Key Results possuem baseline atual e target numérico claro
- [ ] Item 6: A distinção entre committed OKRs e aspirational OKRs está clara
- [ ] Item 7: Trade-offs e prioridades foram discutidos explicitamente durante o setting
- [ ] Item 8: Dependências cross-squad foram identificadas durante a fase de setting
- [ ] Item 9: O backlog de OKRs não selecionados está documentado para referência futura
- [ ] Item 10: Todos os OKRs foram documentados no sistema oficial (ferramenta ou repositório)

### Seção 2 — Cadência de Acompanhamento (Tracking Cadence)
- [ ] Item 11: Check-in semanal de OKRs está acontecendo em cada squad (< 30 minutos)
- [ ] Item 12: O formato do check-in semanal é padronizado (confidence level, blockers, next actions)
- [ ] Item 13: Confidence levels são atualizados semanalmente (on-track, at-risk, off-track)
- [ ] Item 14: Blockers identificados nos check-ins são escalados dentro de 24 horas
- [ ] Item 15: O responsável por atualizar cada Key Result está designado
- [ ] Item 16: Dados para medir Key Results são coletados automaticamente onde possível
- [ ] Item 17: Check-in mensal cross-squad acontece para alinhar dependências
- [ ] Item 18: Dashboard de OKRs está acessível e atualizado para toda liderança
- [ ] Item 19: Alertas automáticos são gerados quando um Key Result fica at-risk

### Seção 3 — Revisão de Ciclo (Cycle Review)
- [ ] Item 20: Retrospectiva de OKRs é agendada antes do início do próximo ciclo
- [ ] Item 21: Cada OKR recebe um score final (0.0 a 1.0) com justificativa
- [ ] Item 22: Learnings de OKRs que falharam são documentados sem blame
- [ ] Item 23: OKRs que superaram expectations são analisados para replicação
- [ ] Item 24: O processo de OKR em si é avaliado (meta-retrospectiva)
- [ ] Item 25: Feedback dos squad leads sobre o processo é coletado formalmente
- [ ] Item 26: Ajustes no processo para o próximo ciclo são definidos e documentados
- [ ] Item 27: O CEO participa da revisão de OKRs do nível empresa

### Seção 4 — Qualidade dos OKRs (OKR Quality)
- [ ] Item 28: Objectives são inspiracionais mas acionáveis (não vagos, não micro-tarefas)
- [ ] Item 29: Key Results medem outcomes, não outputs (resultado, não entrega)
- [ ] Item 30: Nenhum Key Result é binary (sim/não) — todos são graduáveis
- [ ] Item 31: Key Results não são disfarces de tarefas (avoid task-as-KR anti-pattern)
- [ ] Item 32: OKRs estão escritos em linguagem compreensível por toda a organização
- [ ] Item 33: Cada OKR passou por peer review antes da finalização
- [ ] Item 34: OKRs stretch são realmente desafiadores (não confortáveis com label stretch)
- [ ] Item 35: OKRs não conflitam entre squads (sem zero-sum objectives)

### Seção 5 — Integração com Operação (Operational Integration)
- [ ] Item 36: OKRs estão integrados com o processo de alocação de recursos (budget/headcount)
- [ ] Item 37: Performance reviews individuais referenciam contribuição aos OKRs
- [ ] Item 38: Decisões de priorização no dia-a-dia usam OKRs como critério
- [ ] Item 39: Novos projetos ou iniciativas são avaliados contra OKRs antes de aprovação
- [ ] Item 40: O sistema de OKRs está conectado ao roadmap de produto
- [ ] Item 41: Mudanças de prioridade mid-quarter são refletidas formalmente nos OKRs
- [ ] Item 42: Comunicação em all-hands referencia progresso de OKRs

### Seção 6 — Saúde do Sistema (System Health)
- [ ] Item 43: Pelo menos 80% dos squads atualizam OKRs semanalmente no prazo
- [ ] Item 44: O tempo médio de check-in semanal está abaixo de 30 minutos
- [ ] Item 45: Menos de 20% dos OKRs são abandonados mid-quarter sem justificativa formal
- [ ] Item 46: O engajamento com o sistema de OKRs não diminuiu em relação ao ciclo anterior
- [ ] Item 47: Novas lideranças são onboardadas no processo de OKRs em sua primeira semana

## Critérios de Aprovação
O sistema operacional de OKRs é considerado saudável quando:

1. **Mínimo de 85% dos itens do checklist estão completos**
2. **100% dos itens da Seção 2 (Tracking Cadence) estão implementados**
3. **Retrospectiva do ciclo anterior (Seção 3) foi realizada**
4. **Qualidade dos OKRs (Seção 4) aprovada com pelo menos 90% dos itens**
5. **Dashboard de OKRs está funcional e acessível**
6. **Todos os squads participaram do processo de setting dentro do prazo**
7. **O CEO validou os OKRs do nível empresa**

## O que Fazer se Falhar
Se o sistema de OKRs não estiver saudável:

1. **Diagnóstico rápido:** Identificar se o problema é de processo, engajamento ou qualidade
2. **OKR clinic:** Realizar sessão de coaching com squads que estão com dificuldade
3. **Simplificar:** Se o sistema está muito complexo, reduzir número de OKRs e simplificar cadência
4. **Reforçar accountability:** Garantir que check-ins semanais sejam não-negociáveis
5. **CEO sponsorship:** O CEO deve reforçar publicamente a importância do sistema
6. **Treinamento:** Oferecer refresher training se a qualidade dos OKRs está baixa
7. **Ferramentas:** Avaliar se a ferramenta de OKRs está facilitando ou dificultando o processo
8. **Quick fix:** Implementar correções imediatas e agendar revisão completa em 30 dias
