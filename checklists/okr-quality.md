# Checklist de Qualidade — OKRs

## Propósito
Garantir que os OKRs (Objectives and Key Results) definidos sejam focados, mensuráveis, alinhados à estratégia, com stretch realista, livres de métricas de vaidade, time-bound e com owners claros. Este checklist é aplicado como quality gate antes da publicação de OKRs em qualquer nível da organização.

## Quando Aplicar
- No início de cada ciclo de OKRs (trimestral ou conforme cadência definida).
- Quando OKRs são revisados mid-cycle por mudança de contexto.
- Antes de alinhar OKRs entre squads, departamentos ou C-Level.
- Quando um agente gera draft de OKRs para validação.
- Na revisão de OKRs de equipes que reportam ao executivo responsável.

## Agente Responsável
- **Primário:** CoS Agent (Chief of Staff Agent)
- **Revisor:** CEO Agent para OKRs corporativos; VP Agents para OKRs de área
- **Facilitador:** Strategy Advisor Agent

## Checklist

### Foco e Quantidade
- [ ] O número total de Objectives está entre 3 e 5 (não mais)
- [ ] Cada Objective tem entre 2 e 5 Key Results (não mais)
- [ ] Os Objectives cobrem as prioridades mais críticas do período
- [ ] Não há OKRs "de fachada" incluídos apenas por completude
- [ ] Os Objectives representam as apostas mais importantes, não o BAU (business as usual)
- [ ] A lista foi priorizada — está claro qual é o #1 se forçado a escolher
- [ ] OKRs de períodos anteriores que não foram concluídos foram deliberadamente incluídos ou removidos

### Mensurabilidade
- [ ] Cada Key Result tem uma métrica quantitativa ou binária (sim/não)
- [ ] A baseline (ponto de partida) de cada métrica está documentada
- [ ] O target de cada Key Result é um número específico, não um range vago
- [ ] O método de medição está definido (ferramenta, fonte de dados, frequência)
- [ ] É possível verificar o progresso semanalmente, não apenas no final do ciclo
- [ ] Não existem Key Results com linguagem ambígua ("melhorar", "otimizar", "explorar")
- [ ] Cada Key Result tem um mecanismo de tracking automatizado ou semi-automatizado
- [ ] Os leading indicators estão identificados além dos lagging indicators

### Alinhamento Estratégico
- [ ] Cada Objective está vinculado a uma escolha estratégica ou prioridade corporativa
- [ ] O vínculo entre OKR e estratégia está explicitamente documentado
- [ ] Os OKRs de nível inferior se conectam (cascade) aos de nível superior
- [ ] Não existem OKRs órfãos (sem conexão estratégica)
- [ ] Os OKRs cross-functional têm co-owners definidos
- [ ] As dependências entre OKRs de diferentes equipes estão mapeadas
- [ ] Os OKRs não conflitam entre si (verificação de consistência)
- [ ] O alinhamento vertical (CEO > VP > Squad) está verificado

### Stretch Realista
- [ ] Os targets representam 60-70% de probabilidade de atingimento (stretch zone)
- [ ] Nenhum Key Result é trivialmente fácil (100% de certeza de atingir)
- [ ] Nenhum Key Result é impossível (0% de probabilidade)
- [ ] O histórico de performance foi considerado na definição dos targets
- [ ] Os recursos disponíveis (budget, headcount, tempo) suportam os targets
- [ ] O nível de ambição é calibrado — nem sandbagging nem moonshot irresponsável
- [ ] Existe diferenciação entre committed OKRs (must-hit) e aspirational OKRs
- [ ] O impacto de fatores externos foi considerado na calibragem

### Anti-Vaidade (Anti-Vanity Metrics)
- [ ] Nenhum Key Result mede apenas volume sem qualidade (ex: "publicar 10 posts")
- [ ] Métricas de output estão acompanhadas de métricas de outcome
- [ ] Não existem métricas que podem ser gamificadas facilmente
- [ ] Cada Key Result mede algo que o time pode influenciar diretamente
- [ ] Os counter-metrics (métricas de proteção) estão definidos quando necessário
- [ ] Métricas de atividade foram substituídas por métricas de impacto
- [ ] O "so what?" de cada Key Result está claro — por que essa métrica importa?
- [ ] As métricas selecionadas resistem ao teste "se atingirmos isso, realmente celebramos?"

### Time-Bound
- [ ] A data de início e fim do ciclo está definida para cada OKR
- [ ] Os checkpoints intermediários estão agendados (weekly, bi-weekly)
- [ ] O prazo é compatível com o escopo do Objective
- [ ] As datas de revisão mid-cycle estão no calendário
- [ ] O grading final está agendado com data e responsável
- [ ] O ciclo de OKR está sincronizado com o ciclo de planejamento da empresa

### Ownership Claro
- [ ] Cada Objective tem exatamente um owner nomeado (pessoa, não equipe)
- [ ] Cada Key Result tem um owner ou contributor específico
- [ ] O owner tem autoridade e recursos para influenciar o resultado
- [ ] O owner aceitou a responsabilidade explicitamente (não foi atribuído sem consulta)
- [ ] O mecanismo de accountability está definido (check-ins, reviews)
- [ ] O escalation path está claro quando um KR está em risco

## Critérios de Aprovação
- Máximo de 5 Objectives, cada um com 2-5 Key Results mensuráveis.
- 100% dos Key Results com métrica quantitativa e baseline documentada.
- 100% dos Objectives vinculados à estratégia corporativa.
- Todos os owners nomeados e confirmados.
- Nenhuma métrica de vaidade identificada sem counter-metric.
- Calibragem de stretch validada por pelo menos um revisor.

## O que Fazer se Falhar
1. Destacar os itens específicos que falharam e devolver ao owner para correção.
2. Realizar sessão de calibração com pares para ajustar ambição e foco.
3. Se o problema for falta de dados para baseline, definir sprint de instrumentação.
4. Se houver excesso de OKRs, facilitar sessão de priorização forçada (stack rank).
5. Registrar padrões de falha no RalphLoop para melhorar o processo no próximo ciclo.
6. Não publicar OKRs que não passem pelo quality gate.
